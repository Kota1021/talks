# 人名は「姓＋名」ではない

「人名は姓と名の2要素から成る」という前提は、それに当てはまらない人を締め出す。

---

# 1. 結論：名前はどのような構造で扱うべきか

## 原則

**名前は「本人が申告した原本の文字列」と「用途ごとに作る派生表現」の2層で扱う。**

- 原本は分割せず、必須の構造も持たせず、書き換えない。
- 分割、読み、ローマ字表記、照合キー、外部システム向けの値は、すべて原本とは別に持つ派生表現とする。
- これは国際規格（ICAO Doc 9303）が採っている構造そのものである。旅券は、各国の文字で書いた目視欄（VIZ）を原本とし、機械読取欄（MRZ）を意図的に情報を落とした派生表現として扱う。

## データ構造

```text
PersonName
├─ fullName            : String     // 原本。必須。入力されたまま保存
├─ components?         : 任意       // 分割が必要な用途のときだけ持つ
│   ├─ primary         : String     // 第一識別子（姓に相当。分けられなければ名前全体）
│   └─ secondary?      : String     // 第二識別子（名に相当）。空でもよい
├─ phonetic?           : String     // 読み。本人が入力する
├─ latin?              : String     // ラテン文字表記。本人が入力する（自動生成しない）
├─ preferredName?      : String     // 呼びかけに使う名前
├─ honorific?          : String     // 敬称・称号。自由入力
├─ aliases[]           : 種別付き   // 通称・以前の氏名・職業上の名前
├─ history[]           : 有効期間付き // 変更履歴
├─ note?               : String     // Unicodeで表せない字などの補足
└─ derived             : 原本から生成する値（原本の側には書き戻さない）
    ├─ matchKey        : 照合用に正規化した値（NFKC＋casefoldなど）
    ├─ sortKey         : 並べ替え用のキー（本人入力かロケール規則に従う）
    └─ exports{}       : 外部システム向けに変換した値（本人が確認・編集）
```

## 規則

| # | 規則 | 根拠 |
|---|---|---|
| 1 | 用途（照合・表示・呼びかけ・並べ替え・外部連携）を先に決め、必要なものだけを集める | GOV.UK、USWDS |
| 2 | 正となる欄は「氏名（全体）」1つにし、入力されたまま保存する | GOV.UK、誤謬#30 |
| 3 | 分割が必要なら、第一識別子／第二識別子の考え方で分け、**第二識別子は空でもよい** | ICAO 9303 |
| 4 | 字種はUnicodeを全面的に受け付ける。拒否するのは制御文字と不可視文字程度 | GOV.UK、誤謬#9 |
| 5 | 長さに小さな上限を設けない（目安は1欄128文字以上） | USWDS、誤謬#6 |
| 6 | 読みやラテン文字表記は本人に入力してもらい、自動でローマ字化した値を正としない | ICAO付録B、誤謬#30 |
| 7 | 敬称・称号は別の任意欄にし、名前から勝手に削らない | ICAO 3.4、GOV.UK |
| 8 | 正規化は照合用の派生キーにだけ使い、原本は書き換えない | 誤謬#38 |
| 9 | 名前を一意キーや同一人物の判定に使わない | 誤謬#21〜#23 |
| 10 | 変更履歴と複数の名前を持てるようにし、ラベルは「旧姓」ではなく「以前の氏名」にする | USWDS、W3C |
| 11 | 「お呼びする名前」の欄を別に設ける | USWDS、W3C |
| 12 | 本名の欄に不適切語フィルタをかけず、1文字の名前も拒否しない | USWDS、誤謬#31 |
| 13 | 外部連携用の値は明示的な規則で派生させ、別に保存する | ICAO（MRZの生成規則） |
| 14 | Unicodeで表せない字に備えて補足欄を用意する | 誤謬#11 |

## 一言でいうと

**分割しない、必須にしない、書き換えない、文字を絞らない。**

# 2. アンチパターン：実サービスの例

調査方法: Playwrightでダミー値を入力し、検証メッセージを観察した（2026年10月時点）。アカウントの作成・確定には一度も到達させていない。

## AP1：姓と名を両方必須にし、1語の名前を裏技で吸収させる

| サービス | 観察した挙動 |
|---|---|
| 楽天（旧フォーム） | 姓だけ・名だけは拒否。**同じ語を両方に入れると通る** |
| Facebook | 姓または名が空だと「短すぎます」で拒否。1語の名前はフォームの外で申請させ、その申請でも「同じ名前を両方の欄に入れて送信」と案内している |
| Apple | 姓だけ・名だけは拒否（ミャンマー名を名の欄だけに入れて確認） |

インドネシア、ミャンマー、タミル系などの人は、正しい名前のままでは登録できない。

## AP2：文字コードの都合で文字種を絞る

**楽天（旧フォーム）**

境界はJIS X 0208相当で、拒否された入力は次のとおり。
- ü、ë などダイアクリティカルマーク付きの文字
- 異体字（髙、𠮷）、互換漢字（﨑）
- ハングル、簡体字、アラビア文字、ミャンマー文字、シンハラ文字

一方で、キリル文字は通過した。

**ゆうちょダイレクト**

- 氏名欄はカナ1欄だけ。
- 中黒「・」が拒否されるため、「メアリー・アン」のような外国人名の区切りを表現できない。
- このカナ氏名が照合キーになっている。

## AP3：エラーを出さずに書き換える

**楽天（旧フォーム）**

| 入力 | 保存される値 |
|---|---|
| `山<田` | `山`（`<` 以降が消える） |
| `デ ラ トーレ` | `デラトーレ`（スペースが消える） |
| ひらがな・半角カナ | 全角カタカナに変換 |

本人が知らないうちに原本が変わり、後の照合失敗の原因になる。

## AP4：「名前らしさ」を推定で判定する

**Facebook**

- `Müller` は通るのに、`Zoë` は「タイトルまたはシンボル」扱いで拒否される。
- `mcDONALD` は「大文字が多すぎる」、`Dr. Smith` は「ピリオドが多すぎる」で拒否される。
- 実在の長い名前（`Pablo Diego Jose Francisco de Paula Juan`）は「有名人と同じ名前」として拒否される。
- シンハラ文字の名前は拒否される。

**Slack**

- 英語の予約語に `ja` と `ms` が含まれ、フルネームにも使えない。Jaという名前の人は登録できない。

## AP5：長さの上限が小さい

| サービス | 上限 |
|---|---|
| Apple | 名は32文字 |
| Google | 名は50文字 |
| 楽天 | 各欄85文字 |
| ゆうちょ | 30文字（HTML上の上限） |

USWDSが推奨する1欄128文字に対して、いずれも小さい。

## AP6：制約を利用者の運用で吸収させる

**三重県 e-TUMO apply（電子申請）**

- 読みをカナで表せない場合は「氏」に"シ"、「名」に"メイ"と入力させる。
- 姓が後ろに来る文化の名前は、名を「氏」の欄に入れさせる。
  - 例: `John Fitzgerald Kennedy` → 「氏」John、「名」Fitzgerald Kennedy

**保存されるデータの意味が壊れる。**

## 参考：比較的よい例（Google）

- 姓は任意。
- `Zoë`、`𠮷`、ハングル、アラビア文字、ミャンマー文字、シンハラ文字、文字種の混在はすべて通過。
- 拒否されるのは `<`、絵文字、URL風の文字列だけで、いずれも乱用対策と見られる。

# 3. 背景

## 3.1 名前の実体

### 誤謬リスト

Patrick McKenzie「Falsehoods Programmers Believe About Names」（2010）は40項目の誤った前提を挙げている。一部を抜粋する。

- 人には正確に1つのフルネームがある（#1）
- 名前は決まった文字数に収まる（#6）
- 名前はASCIIで表せる（#9）
- 名前はUnicodeで表せる（#11）
- 名前には家族で共有される部分がある（#18）
- 人には名前がある（#40）

### 世界の名前の構造

**姓がない／大半が姓を持たない**
- **インドネシア**: 1語だけの名前もある（スカルノ、スハルト）。旅券にも姓名の区別がない。
- **ミャンマー**: 姓の伝統がなく、名前全体が個人名。
- **タミル系**（スリランカ・南インド）: 「父の名＋本人の名」。父の名は頭文字にされることが多い（A. Rasiah）。
- **ソマリア**: 「本人の名＋父の名＋祖父の名」。
- **アフガニスタン**: 伝統的に姓がない。

**姓に見えるが、実は父称**
- **アイスランド**: 父の名＋-son／-dóttir。
- **マレーシア**: Isa bin Osman のように bin（〜の息子）で父の名をつなぐ。
- **アラブ圏**: 本人・父・祖父の名を連ねる。

**日本にない構成要素がある**
- **シンハラ系**: 家系名（gē名）＋名＋姓。家系名は頭文字にされたり省かれたりする。
- **シク教徒**: 名＋Singh／Kaur。姓は伝統的に使わない。

**姓が2つ以上ある**
- **スペイン語圏**: 父方と母方の2つの姓。
- **ブラジル**: 3〜4つの姓もある。

**制度の揺れ（インドネシア）**
- 2022年の内務大臣令73号で「最低2語・最大60字」の基準ができた。
- ただし当局者は、1語でも本人が強く望めば認めると説明している。運用の実態は**未検証**。

### 人数の規模（フェルミ推定）

直接のデータはない。人口は国連の世界人口推計2024年版の概数（出典は未取得）。

| 定義 | 推定 | 幅 |
|---|---|---|
| 世襲の姓があり、2欄に分けられる | 約80%（約65億人） | 75〜85% |
| 日本型（姓1語＋名1語） | 約45%（約36億人） | 35〜55% |

- 日本型の約4割は中国の人口による。
- **2欄に収まらない約2割（15〜17億人）は、インド一国の人口に匹敵する。**

## 3.2 国際規格

### ICAO Doc 9303 Part 3（旅券。ISO/IEC 7501が参照）

- 名前は「姓／名」ではなく、**第一識別子／第二識別子**として定義されている。
- 分けられない場合は、**名前全体を第一識別子**とする。
- 目視欄（VIZ）は各国の文字のままで、機械読取欄（MRZ）はラテン大文字のみ。MRZの名前はVIZと同じ形にならない場合がある。
- MRZの名前は、規定の手順で切り詰める場合を除き切り詰めない。記号の扱い（アポストロフィは削除、ハイフンは区切り文字）も定められている。
- 敬称や称号は、法的に名前の一部でない限り載せない。

### ISO/IEC 18013-5（モバイル運転免許証）

- `family_name` は「姓、名字、または第一識別子」と定義されている。
- Unicode表記用の要素が別にある。
- いずれも二次情報による。ISO原文は有償のため未取得。

### 日本の制度

- 2025年5月26日から、戸籍の記載事項に氏名のフリガナが加わった。読み仮名は公証される情報になった。

## 3.3 手本になるもの

### 設計の基準

**GOV.UK Design System（英国政府）**
- 1欄の「Full name」を例として示している。
- 数字や記号を含め、利用者が必要とする文字をすべて受け付けるよう求めている。
- 分割すると、名前がその形式に収まらない危険が増すと明記している。
- 名前の変更を容易にするよう求めている。

**USWDS（米国政府）**
- 各欄128文字まで受け付ける。1文字の名前も受け付ける。
- **どの欄も必須にしない**（インドネシアやアイスランドには1語の名前の人がいるため）。
- 大文字小文字を正規化しない。
- 「旧姓」ではなく「以前の名前」を尋ねる。
- 呼びかけ用の名前を別の欄で受け取る。

### 実サービス

| サービス | 良い点 | 限界 |
|---|---|---|
| Google | 姓が任意。文字の制限が緩い | 名は50文字まで |
| GitHub | 名前はName欄1つ。実名と一致させる必要がないと明記 | 名前の入力は必須 |
| Slack | フルネームと表示名の2層 | 予約語 `ja`／`ms` |
| Wise（本人確認あり） | 法的な氏名と呼んでほしい名前を分離。改名は書類で変更。姓名の欄がない身分証明書にも対応 | **2語以上が条件**で、1語の名前は通らない |

単独で満点のサービスは見つからなかった。結論の構造は次の要素を組み合わせたもの。

- USWDSの骨格（必須欄なし、1欄128文字、正規化しない）
- Wiseの2層構造（法的な氏名と呼び名を分ける）
- Wiseの「2語以上」条件は外す
