Personal names, field-tested

人名は「姓＋名」ではない

「人名は姓と名の2要素から成る」という前提は、それに当てはまらない人を締め出す。
2欄に収まらない人は 約2割、15〜17億人。

1. 結論：名前はどのような構造で扱うべきか

原則

名前は「本人が申告した原本の文字列」と「用途ごとに作る派生表現」の2層で扱う。

  • 原本は分割せず、必須の構造も持たせず、書き換えない。
  • 分割、読み、ローマ字表記、照合キー、外部システム向けの値は、すべて原本とは別に持つ派生表現とする。
  • これは国際規格（ICAO Doc 9303）が採っている構造そのものである。旅券は、各国の文字で書いた目視欄（VIZ）を原本とし、機械読取欄（MRZ）を意図的に情報を落とした派生表現として扱う。

データ構造

PersonName
├─ fullName            : String     // 原本。必須。入力されたまま保存
├─ components?         : 任意       // 分割が必要な用途のときだけ持つ
│   ├─ primary         : String     // 第一識別子（姓に相当。分けられなければ名前全体）
│   └─ secondary?      : String     // 第二識別子（名に相当）。空でもよい
├─ phonetic?           : String     // 読み。本人が入力する
├─ latin?              : String     // ラテン文字表記。本人が入力する（自動生成しない）
├─ preferredName?      : String     // 呼びかけに使う名前
├─ honorific?          : String     // 敬称・称号。自由入力
├─ aliases[]           : 種別付き   // 通称・以前の氏名・職業上の名前
├─ history[]           : 有効期間付き // 変更履歴
├─ note?               : String     // Unicodeで表せない字などの補足
└─ derived             : 原本から生成する値（原本の側には書き戻さない）
    ├─ matchKey        : 照合用に正規化した値（NFKC＋casefoldなど）
    ├─ sortKey         : 並べ替え用のキー（本人入力かロケール規則に従う）
    └─ exports{}       : 外部システム向けに変換した値（本人が確認・編集）

規則

#番号は McKenzie「Falsehoods Programmers Believe About Names」の項目番号。

#規則根拠
1用途（照合・表示・呼びかけ・並べ替え・外部連携）を先に決め、必要なものだけを集めるGOV.UK、USWDS
2正となる欄は「氏名（全体）」1つにし、入力されたまま保存するGOV.UK、誤謬#30
3分割が必要なら、ICAOの第一識別子／第二識別子の考え方で分け、第二識別子は空でもよいことにするICAO 9303
4字種はUnicodeを全面的に受け付ける。拒否するのは制御文字と不可視文字程度GOV.UK、誤謬#9
5長さに小さな上限を設けない。上限は乱用対策として十分に大きく取る（目安は1欄128文字以上）USWDS、誤謬#6
6原文字・ラテン文字・読みは別の欄にし、本人に入力してもらう。自動でローマ字化した値を正としないICAO付録B、誤謬#30
7敬称・称号は別の任意欄にし、名前から勝手に削らないICAO 3.4、GOV.UK
8照合用の正規化は派生キーとして作り、原本は書き換えない。NFCでもCJK互換漢字は別の字に置き換わる誤謬#38
9名前を一意キーや同一人物の判定に使わない誤謬#21〜#23
10変更履歴と複数の名前を持てるようにし、ラベルは「旧姓」ではなく「以前の氏名」にするUSWDS、W3C
11「お呼びする名前」の欄を別に設けるUSWDS、W3C
12並べ替えのキーは本人の入力か、ロケールの規則に従うW3C
13本名の欄に不適切語フィルタをかけず、1文字の名前も拒否しないUSWDS、誤謬#31
14外部連携用の値は明示的な規則で派生させ、別に保存する。本人に確認・編集してもらうICAO（MRZの生成規則）
15Unicodeで表せない字に備えて補足欄を用意する誤謬#11

一言でいうと

分割しない、必須にしない、書き換えない、文字を絞らない。

インドネシア、ミャンマー、タミル系などの人は、正しい名前のままでは登録できない。

AP2

文字コードの都合で文字種を絞る

楽天（旧フォーム）

拒否された入力（「登録できない文字があります」）:

  • ダイアクリティカルマーク付きの文字（ü、ë）
  • 異体字（髙、𠮷）、互換漢字（﨑）
  • ハングル、簡体字、アラビア文字、ミャンマー文字、シンハラ文字
  • 絵文字、丸数字

通った入力: キリル文字（Иванов）、数字、O'Brien-Smith

通る文字と拒否される文字の境界はJIS X 0208とよく一致する。ページ自体はUTF-8なので、制約はバックエンド側にあると推測する。フリガナ欄では中黒「・」も拒否される。

ゆうちょダイレクト（新規利用申込み）

  • 氏名欄は「氏名（カナ）」の1欄だけで、姓名を分割しない。そのため1語の名前はそのまま入力できる。
  • 拒否された入力: ひらがな、半角カナ、漢字、中黒「・」。「メアリー・アン」のような外国人名の区切りを表現できない。
  • 通った入力: ラテン文字、ハイフン、ピリオド、括弧、スペース。
  • 規定には、カナ氏名が一致しないと申し込めない旨の条項がある。このカナ氏名が照合キーになっている。
  • 試行を重ねたところ「一定回数誤りが続きましたのでログアウトしました」と表示されたため、検証を打ち切った。

楽天もゆうちょも文字の範囲が狭く、ベトナム語・韓国語・多くのヨーロッパ系の名前は本来の綴りで登録できない。

AP3

エラーを出さずに書き換える

楽天（旧フォーム）

山<田→山　（< 以降が消える）
デ ラ トーレ→デラトーレ　（スペースが消える）
ひらがな・半角カナ→全角カタカナ

最も危険な類型。本人が知らないうちに原本が変わり、後の照合失敗の原因になる。

長さの上限が小さい

サービス上限
Apple名は32文字（調査した中で最も厳しい）

AP6

制約を利用者の運用で吸収させる

三重県 e-TUMO apply（電子申請）

システムの制約を回避するため、県は利用者に次のように案内している。

  • 読みをカナで表せない場合は、「氏」に"シ"、「名」に"メイ"と入力する。
  • 姓が後ろに来る文化の名前は、名を「氏」の欄に、姓を「名」の欄に入れる。
    例: John Fitzgerald Kennedy → 「氏」John、「名」Fitzgerald Kennedy

保存されるデータの意味が壊れる。

参考

比較的よい例（Google）

  • 姓は任意。
  • 名のみの入力、1文字の名前、数字、Zoë、𠮷、ハングル、アラビア文字、ミャンマー文字、シンハラ文字、文字種の混在はすべて通過。
  • 拒否されたのは <、絵文字、URL風の文字列、空白のみ、51文字以上。多くは乱用対策と見られる。

観察から言えること

  1. 姓を必須にするかどうかは、照合キーの設計で決まっている。表示用の名前を扱うGoogleは姓を任意にし、身元照合を重視するFacebook・楽天・Appleは姓と名を両方必須にしている。1語の名前は「同じ語を両方の欄に入れる」という裏技で扱われている。
  2. 国産サービスは文字セットが狭い。楽天はJIS X 0208相当、ゆうちょはカタカナ中心。
  3. 黙った書き換えが最も危険。本人が知らないうちに原本が変わり、後で照合に失敗する原因になる。
  4. 推定による判定は、正当な名前を誤って拒否する。Facebookの Zoë が例。

3. 背景

3.1 名前の実体

誤謬リスト

Patrick McKenzie「Falsehoods Programmers Believe About Names」（2010）は、プログラマーが名前について無自覚に置いている前提を40項目にわたって否定した。その一部を抜粋する。

  • 人には正確に1つのフルネームがある（#1）
  • 名前は決まった文字数に収まる（#6）
  • 名前はASCIIで表せる（#9）
  • 名前はUnicodeで表せる（#11）
  • 名前には少なくとも1つ、家族で共有される部分がある（#18）
  • 人には名前がある（#40）

このトークでは「姓＋名の2要素」という前提に絞り、それが実際に誰をどう締め出しているかを、規格・人口・実サービスの3方向から確認する。

世界の名前の構造

出典は英国政府作成・インターポール配布の命名慣習ガイド（2006）、W3C「Personal names around the world」、各種報道。

姓がない／大半が姓を持たない

国・地域構造
インドネシア多くの人に姓がない。1語だけの名前もある（スカルノ、スハルト）。旅券にも姓名の区別がない
ミャンマー姓の伝統がなく、名前全体が個人名。「U」のような敬称が名前と一体化する
タミル系（スリランカ・南インド）「父の名＋本人の名」。父の名は頭文字にされることが多い（A. Rasiah）
ソマリア「本人の名＋父の名＋祖父の名」。本人を特定するには3つすべてが必要
アフガニスタン伝統的に姓がない

姓に見えるが、実は父称

  • アイスランド: 父の名＋-son／-dóttir。電話帳は名で並ぶ。
  • マレーシア: Isa bin Osman のように、bin（〜の息子）で父の名をつなぐ。
  • アラブ圏: 本人・父・祖父の名を連ねる。同じ人が複数の正当な形で名乗る。

日本にない構成要素がある

  • シンハラ系: 家系名（gē名）＋名＋姓。家系名は頭文字にされたり省かれたりし、農村部では姓がないこともある。
  • シク教徒: 名＋Singh／Kaur。姓は伝統的に使わない。

姓が2つ以上ある

  • スペイン語圏: 父方と母方の2つの姓。
  • ブラジル: 3〜4つの姓もある。並び順はスペイン語圏と逆。

制度も揺れている（インドネシア）

  • 2022年の内務大臣令73号で、名前の登録基準は「最低2語・最大60字」になった。
  • ただし当局者は、1語でも本人が強く望めば認めると説明している。
  • 2022年以前に登録された1語の名前は今も有効。
  • 運用の実態は未検証（2025年の報道では「1語は不受理」とされている）。

人類の何割が「姓＋名」に収まるか（フェルミ推定）

直接のデータは見つからなかった。人口は国連の世界人口推計2024年版の概数を使っている（出典は未取得）。

定義内容推定幅
広義世襲の姓があり、姓欄と名欄に分けられる約80%（約65億人）75〜85%
狭義日本型（姓1語＋名1語。ミドルネーム・複数の姓・父称なし）約45%（約36億人）35〜55%
  • 結果を最も大きく左右するのはインド（±2.7ポイント）とアフリカ（±2ポイント）。
  • 日本型（狭義）の約4割は中国の人口であり、日本型が多数派に見えるのは中国の人口の大きさによる。
  • 広義で漏れる約2割（15〜17億人）は、インド一国の人口に匹敵する。

「姓を必須にする」という設計は、外れ値ではなく十数億人を相手にしている。

3.2 国際規格は2要素を前提にしていない

ICAO Doc 9303 Part 3（旅券。ISO/IEC 7501が参照）

  • 名前は「姓／名」ではなく、第一識別子／第二識別子として定義されている。
  • 名前を2つに分けられない場合は、名前全体を第一識別子とする。第二識別子は空でもよい。
  • 目視欄（VIZ）は各国の文字のままで、機械読取欄（MRZ）はラテン大文字のみ。MRZは意図的に情報を落とした派生表現であり、MRZの名前はVIZと同じ形にならない場合がある。
  • MRZの名前は、規定の手順で切り詰める場合を除き切り詰めない。アポストロフィは削除し、ハイフンは区切り文字に置き換える。
  • 敬称や称号は、法的に名前の一部でない限り載せない。

ISO/IEC 18013-5（モバイル運転免許証）

  • family_name は「姓、名字、または第一識別子」と定義されている。
  • Unicode表記用の要素が別に用意されている。
  • いずれも二次情報による。ISO原文は有償のため未取得。

読み取れること: 規格は「原本の名前」と「用途ごとの派生表現」を分けて扱い、2要素への分割を必須にしていない。入力フォームが規格から借りるべきなのは、MRZのA–Zや39文字といった制約ではなく、この構造である。

日本の制度

2025年5月26日から、戸籍の記載事項に氏名のフリガナが加わった。読み仮名は公証される情報になった。

3.3 手本になるもの

設計の基準

GOV.UK Design System（英国政府）

  • 1欄の「Full name」を例として示している。
  • 数字や記号を含め、利用者が必要とする文字をすべて受け付けるよう求めている。
  • 分割すると、名前がその形式に収まらない危険が増すと明記している。
  • 名前の変更を容易にするよう求めている。

USWDS（米国政府）

  • 各欄128文字まで受け付ける。1文字の名前も受け付ける。
  • どの欄も必須にしない。インドネシアやアイスランドには1語の名前の人がいることを理由に挙げている。
  • 大文字小文字を正規化しない。
  • 「旧姓」ではなく「以前の名前」を尋ねる。
  • 呼びかけ用の名前を別の欄で受け取る。

実サービス

サービス良い点限界
Google姓が任意。文字の制限が緩い名は50文字まで
GitHub（表示用）名前はName欄1つ。プロフィールの名前は実名と一致させる必要がないと明記名前の入力は必須
Slack（表示用）フルネーム（必須）と表示名（任意）の2層予約語 ja／ms
Wise（本人確認＝KYC あり）法的な氏名と呼んでほしい名前を分離。改名は書類で変更。姓名の欄がないインドネシアやマレーシアの身分証明書にも対応2語以上が条件で、1語の名前は通らない

単独で満点のサービスは見つからなかった。最も理想に近いのは次の組み合わせで、1章の結論の構造はこれを基にしている。

  • 骨格はUSWDS（必須欄なし、1欄128文字、正規化しない）
  • Wiseの「法的な氏名」と「呼び名」の2層構造
  • Wiseの「2語以上」条件は外す
  • 本人確認をしない用途なら、GitHubのように実名との一致を求めない

まとめ

「姓＋名」に収まらない人は、例外ではなく十数億人いる。

  • 国際規格すら2要素を前提にしておらず、「原本」と「派生表現」を分けて扱っている。
  • 実サービスの多くは2要素を前提にしたまま、1語の名前を裏技や人手の手続きで吸収している。
  • 対策は難しくない。分割しない、必須にしない、書き換えない、文字を絞らない。
